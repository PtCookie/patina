# Patina

Patina is a design system for web, Slint desktop and Android apps. This repo turns the design tokens into things projects can consume: a **shadcn registry**, a **Slint token file** and **Android Material 3 theme files**, all served as static files from **Cloudflare Workers** at `patina.ptcookie.net`.

Write code, comments and all documentation in English.

## Status

- The design is done. `design-system/` is the committed snapshot: `tokens.json`, `README.md` (visual language and UI copy rules), `Android.md`, component previews (`components/*/preview.html` + `bundle.css`/`bundle.js`) and licence texts. Namespace `Patina`, class prefix `pt-`. "Mist" names the neutral palette only.
- Helper scripts are in `tools/`: `cc.py` (oklch to sRGB + WCAG contrast), `m3.py` (Android role mapping), `tokens_css.py` (tokens to CSS).
- Built: the token parser, the checks (derived tokens, contrast, Android pairs) and the generators for the registry base item, `tokens.slint` and the Android files (`pnpm build`). All 25 design-system components are built for the web (`registry/ui/*.tsx`, served as `@patina/<name>`). The Slint library has three tiers of compact desktop components (`slint/`, see "Slint library" below), and the Android library has two tiers of Compose wrappers (`android/`, see "Android library" below; compiled and run on an emulator). The registry is deployed. The documentation site is built (`site/`). Not built, on purpose: DesktopShell and Cover as library components. They are whole-screen and brand compositions that exist as previews (and as the gallery's `Shell` window and the README images), not parts that an app imports.
- Adopting Patina in a consuming project happens only after the registry is deployed and the maintainer says so.

## Source of truth

- `design-system/tokens.json` is the single source for every generated file. Never hand-edit generated output.
- Token changes are decided by the maintainer. Do not change a token as a side effect of another task; raise it first.
- `design-system/VERSION` identifies the snapshot. Stamp its content into the header of every generated file.
- The build reads only files in this repo. It never fetches tokens over the network.

## Decisions (settled)

**System**
- The design system is the standard; consuming projects align to it, not the other way round.
- Web = shadcn/ui **Luma** lineage + Base UI + Tailwind 4 + Astro. The radius scale is tighter than Luma: `xs 2 · sm 4 · md 6 · radius 8 · xl 10 · 2xl 12 · 3xl 16 · full`. Buttons, inputs and selects default to `radius` (8px); `radius-full` is the opt-in **pill** option (`shape="pill"`).
- Desktop (Slint) = same tokens + `compact-*` density tokens.
- Android (Compose, Material 3, minSdk 31) = **static** M3 scheme generated from tokens, not dynamic colour. Rules are in `design-system/Android.md`; `tools/m3.py` is the reference implementation of the role mapping and the source of the hex values in that table (it writes them to `m3.json`).
- Headings use the `heading` family (JetBrains Mono).
- Colours are used **only by semantic token name**. Components never compute state colours (no `color-mix`, no ad-hoc opacity); every derived colour is a token.
- It is a general design system, not "developer tools"; do not describe it that way.

**Fonts** (all SIL OFL 1.1; Phosphor icons are MIT; texts in `design-system/assets/Licenses/`)
- Families: `sans` Inter + Pretendard · `heading` JetBrains Mono + Pretendard · `mono` JetBrains Mono + D2Coding · `mono-ko` D2Coding · `serif` Newsreader + MaruBuri.
- **Reserved Font Names: Pretendard, D2Coding, MaruBuri.** OFL treats a format change (TTF to woff2) or subsetting as a modification, so for these three use only the official files unmodified, or rename the derivative. Never convert or subset them, and never use a third-party repackaging of them.
- Delivery per font:
  - **Inter, JetBrains Mono, Newsreader**: Fontsource variable packages (`@fontsource-variable/*`) as project dependencies. Fontsource is self-hosting: the files are bundled into the project's own output and no CDN is involved. They have no Reserved Font Name, so Fontsource's converted, unicode-range-split files are licence-safe.
  - **Pretendard on the web**: the `pretendard` npm package's official dynamic-subset (`pretendard/dist/web/variable/pretendardvariable-dynamic-subset.css`). It is the official build, not our subset. Slint and Android bundle the official Pretendard files.
  - **D2Coding, MaruBuri**: official files copied into the project's `public/fonts`. The Workers site serves them at `/fonts/*` so projects can download them. Official MaruBuri OTF is used as is (no woff2). The repo keeps them in `fonts/` (D2Coding Regular and Bold TTF from release 1.4.0, MaruBuri Regular, SemiBold and Bold OTF), renamed only as files; `fonts/SHA256SUMS` pins the exact bytes and `pnpm build` fails on any difference, a missing file or a stale entry (`src/fonts.ts`). The build serves them with their OFL texts and `fonts/patina-fonts.css`, generated from the `type.fonts` entries of `tokens.json` (relative urls, `font-display: swap`). To update a font, replace the file with the new official release, run `shasum -a 256` into `fonts/SHA256SUMS`, and review the diff.
- Registry JSON cannot carry binaries. A registry item declares the Fontsource packages as `dependencies`, and ships only the font-family stacks and the `@font-face` CSS for the copied fonts.
- Copy the matching licence text next to every font file you ship (OFL condition 2).
- Verified from the published packages (`@fontsource-variable/*` 5.3.0, `pretendard` 1.3.9): they register `Inter Variable`, `JetBrains Mono Variable`, `Newsreader Variable` and `Pretendard Variable`, and italics are separate files (`@fontsource-variable/<font>/wght-italic.css`). The tokens keep the plain family names, which Slint and Android use; only the web output rewrites them (`webFontStack` in `src/emit/css.ts`).

**Hosting**
- Registry and token files are plain static files on **Cloudflare Workers Static Assets** (atomic deploys, preview URLs), not R2 and not GitHub. R2 stays an option only for binaries.
- Domain: `patina.ptcookie.net`.
- URL space: `/r/{name}.json` (+ `/r/registry.json`), `/slint/patina-slint.tar.gz` (the whole Slint library), `/slint/patina.slint` (entry), `/slint/tokens.slint`, `/slint/components/*.slint`, `/tokens/tokens.json`, `/android/{Color,Type,Shape,Size,Icons}.kt`, `/android/PatinaTheme.kt`, `/android/components/*.kt`, `/android/patina-android.tar.gz` (the whole Android library), `/fonts/*`, the documentation site (`/`, `/ko/`, `/guide/…`, `/components/<name>/`, `/preview/<name>/`, `/404.html`, `/pagefind/`, `/_astro/`, `/sitemap-*.xml`), and the agent documentation: `/llms.txt`, `/llms-full.txt`, `/guide.md`, `/agents-snippet.md`, `/design.md`, `/android.md`, `/components/{name}.md`.
- Slint and Android consumers **vendor** the generated files (download once, commit) instead of fetching at their build time. Generated files carry a header with the source version.
- The shadcn CLI fetches from Node, so CORS is not expected to matter (not confirmed by docs). Verify with a real install.

## Build pipeline

One TypeScript build script, no separate tools: `design-system/tokens.json` to `public/`, then `wrangler deploy`.

1. Parse tokens (value grammar below), resolve `{refs}` per theme.
2. **Checks that fail the build:** WCAG contrast for the text/fill pairs (see below); every derived token equals its recipe recomputed from its base token; no unresolved refs; Android M3 pairs ≥ 4.5:1 and `outline` ≥ 3:1 (`design-system/Android.md`).
3. Generate: shadcn registry items (`:root` / `.dark` cssVars, fonts CSS), `tokens.slint`, Android `Color.kt` / `Type.kt` / `Shape.kt`.
4. Alpha tokens are checked **composited over their background**; Slint gets `#RRGGBBAA`, Android `Color(0xAARRGGBB)`. oklch to sRGB must clamp gamut the way `tools/cc.py` does so web, Slint and Android agree.

The generator emits `:root` / `.dark` for class-based dark mode. It leaves the `@custom-variant` line out (the shadcn CLI writes `&:is(.dark *)` itself), and consumers set it to `@custom-variant dark (&:is(.dark, .dark *))` so that `dark:` utilities also match `<html>` itself; `docs/agent-guide.md` says so. The component previews use `[data-theme]` for demo purposes only.

Port `cc.py` / `m3.py` to TypeScript rather than shelling out to Python. Keep their numbers as test fixtures: `m3.py` prints the contrast of every M3 pair and writes the resulting hex values to `m3.json`.

### tokens.json grammar

```
name, version, meta
color.themes[{id,name}]  color.tokens[{name, value, usage}]
   value = "oklch(L C H)" | "oklch(L C H / A%)" | "{other-token}"      (single string: same in both themes, e.g. sidebar-ring)
         | { "light": …, "dark": … }
type.fonts[{family,file,weight,style}]  type.families{sans,heading,mono,mono-ko,serif}  type.groups[{name,family,styles[…]}]
spacing / radius / size / shadow : { note, tokens[{name, value, usage}] }   (shadow values may be { light, dark })
```

- Keep `tokens.json` within this grammar.
- Names with dots exist (`space-1.5`); the CSS custom property is `--space-1\.5`.
- `usage` strings starting with `ADDED.` mark tokens that are not in the shadcn preset `b3JSmtB71E`; keep that distinction in generated docs.
- Alpha is part of the value on purpose (no `{x}/10%` reference syntax). Derived values are concrete and the build verifies them.
- `type.fonts` lists the files used by the component previews. Consumers use the delivery paths in "Fonts".

### Derived tokens (the build must recompute these)

Alpha scale means `base alpha × pct` (dark `input` is already `oklch(1 0 0 / 15%)`, so `input@50%` is 7.5%).

| token | light | dark |
|---|---|---|
| `primary-hover` | `primary`@80% | same |
| `secondary-hover` | `secondary` mixed 5% toward `foreground`, in oklch, shorter hue arc, opaque | same |
| `muted-hover` | `muted`@50% | same |
| `ghost-hover` | `{muted}` | `muted`@50% |
| `outline-hover` | `{muted}` | `input`@30% |
| `tab-active` | `{background}` | `input`@30% |
| `tab-foreground` | `foreground`@60% | same |
| `control` / `control-strong` | `input`@50% / @90% | same |
| `kbd` | `muted-foreground`@10% | same |
| `destructive-muted` | `destructive`@10% | @20% |
| `destructive-muted-hover` | `destructive`@20% | @30% |
| `invalid-ring` / `invalid-border` | `destructive`@20% / @0% | @40% / @50% |
| `overlay` | black@30% | same |
| `outline-fill` | `{background}` | transparent |
| `switch-thumb` / `switch-thumb-checked` | `{background}` / `{background}` | `{foreground}` / `{primary-foreground}` |
| `primary-muted` | `link`@10% | `link`@20% |
| `success/warning/info-muted` | base@10% | base@20% |
| `shadow-card-hover` | `shadow-card` with ring alpha doubled (5 to 10%) | (10 to 20%) |

### Contrast baselines

Targets are in each token's `usage` (e.g. `muted-foreground` ≥ 4.5 on `background`/`card`, `link` ≥ 4.8 light / 5.9 dark, `ring` ≥ 3:1). `design-system/README.md` § Accessibility states the guarantees: every text colour ≥ 4.5:1 on the background named in its usage note (both themes), `muted-foreground` 4.7:1 on `muted`, `destructive` 4.8:1 on its own tint over `background` (4.5:1 over `card`), `ring` ≥ 3:1 on `background`/`card`/`muted`; `border` is decorative (1.25:1) and must not be the only boundary of a control. Recompute all of these in tests; do not trust the prose. Light `muted-foreground`, `ring`, `destructive` and `sidebar-primary` were adjusted away from the preset for contrast; the `link` token exists because dark `primary` is a fill, not a text colour.

## Registry design

- Namespace `@patina` maps to `https://patina.ptcookie.net/r/{name}.json`.
- A `registry:base` item for init (cssVars light/dark, `@theme` mapping for Tailwind 4, font CSS, dependencies) plus **only the components projects actually use**, overridden to carry Patina's radii, pill option, flush menu rows, `link` button, interactive Card, Table `containerClassName`. Everything else is referenced by bare name and resolved from the stock shadcn registry. Do not republish all of shadcn: Luma's radius multipliers conflict with this scale.
- Component source is **hand-maintained TSX** in this repo (Base UI flavour, `@base-ui/react`), not generated from the previews. `design-system/components/*/preview.html` + `bundle.css` are the visual spec; the previews are `pt-` CSS demos, not shippable code.
- Layout: the sources live in `registry/ui/<name>.tsx` and import `cn` from the `cn` package (`import { cn } from "cn"`), the way the stock shadcn components have since September 2026 (changelog "cn"). `cn` is an npm dependency of every item and of the base item, not a registry dependency: no `utils` item is installed, so a project's own `src/lib/utils.ts` (which may hold other helpers and no `cn`) is never overwritten. `cn` is also a dev dependency here, so the sources are type-checked and rendered with the same function. `src/components.ts` lists each component (`COMPONENTS`: name, description, source file, npm dependencies), wraps the source in a `registry:ui` item named like the shadcn component it replaces (so `@patina/button` writes the same file as the stock `button`), and the build fails if a source imports a package that is not declared. A new component is one `.tsx` file plus one `COMPONENTS` entry.
- Rules every component follows (`tests/components.test.tsx` enforces them): colours come only from semantic token utilities (`bg-primary-hover`, `bg-outline-fill`, `text-link`, `bg-destructive-muted` …), never `color-mix()`, `bg-primary/80`-style opacity modifiers, palette classes, colour literals or `dark:` colour overrides; sizes come from the size tokens (`h-(--control-md)`, `size-(--control-sm)`); every conflicting class group is set by exactly one variant (a pill replaces `rounded-lg` instead of stacking on it), so the result does not depend on the project's `cn` merging classes; the pill is the opt-in `shape="pill"`; focus is a 2px `ring` outline with a 2px offset.
- Visual parity with the previews was checked on 2026-10-17: a page with each preview element (`pt-btn`, `pt-badge`, `pt-input`, `pt-card` markup plus `bundle.css`) next to the matching Patina component, compared by computed style (display, size, padding, border, radius, colours, font, gap, shadow, cursor, svg size) for 34 pairs at a 1280px viewport in light and dark: 0 differences. Hover was compared with real pointer hover for the six button variants and the interactive card: identical. The first pass found real gaps that were fixed (buttons lacked `cursor: pointer`, icon buttons had no gap, badges had stock `justify-center`/`overflow-hidden`, the card footer had stock `items-center`). Things to know when repeating it: the preview CSS reads `--space-N` variables that the registry deliberately does not emit (Tailwind's spacing scale equals them), so define them on the page; turn transitions off (`* { transition: none !important }`) or colours are read mid-transition; below 768px the input is 16px by design. The other 14 components were compared the same way on 2026-10-17 (Label, Separator, Skeleton, Table, Checkbox, Toggle, ToggleGroup, Collapsible, Pagination, Popover, DropdownMenu, Sheet, NavigationMenu, Chart: about 70 element pairs in light and dark, popups and the sheet open). It found real defects that are fixed: the Separator never had a size (Base UI marks the orientation as `data-orientation`, not `data-horizontal`), the chart tick labels stayed in Recharts' default grey (Recharts 3 moved the text out of `.recharts-cartesian-axis-tick`), Checkbox and Toggle lacked `cursor: pointer`, the pagination ellipsis lacked the transparent 1px border, and a top-level `NavigationMenuLink` merged with the panel-link layout (now `variant="item"`). Hover was checked with a real pointer for Toggle, a table row and a menu item. What still differs on purpose: `Label` is `flex items-center gap-2` (room for an icon or marker) where the preview label is a block span; the numeric table header is right-aligned (the preview's `.pt-table th` rule beats `.pt-num`, so its header stays left, a preview quirk); table row rules sit on `tr` instead of each cell (same collapsed-border result); toggles do not wrap (`whitespace-nowrap`); the menu surface scrolls (`overflow-y-auto` with a max height) where the preview clips; icons are 16px where the previews use 14px; the navigation panel splits its surface (`Popup`) from its grid (`Content`). Not compared: the chart tooltip and the open/close animations.
  The last seven (Kbd, Switch, Alert, Tooltip, Tabs, Select, Article) were compared the same way afterwards, about 40 pairs in light and dark, and again found real gaps that are fixed: the standalone `Kbd` fill is `muted` (the `kbd` token is the quieter tint for use inside an input, pass `bg-kbd`), `Alert` forced `items-start` on the grid, inline `code` in `Article` took the 20px line height of `text-sm` instead of inheriting 28px, and the article measure was 592px of text instead of 640px (the preview has no `box-sizing` reset, so its `max-width: 640px` is text only; the component is `max-w-172` with 24px padding). On purpose: `Alert` is `w-full` (the preview fixes 420px), a tooltip wraps at `max-w-xs` instead of never wrapping, tabs do not wrap, and `SelectValue` shows the selected item's text without its icon.
- The component set: Alert, Article, Badge, Button, Card, Chart, Checkbox, Collapsible, DropdownMenu, Input, Kbd, Label, NavigationMenu, Pagination, Popover, Select, Separator, Sheet, Skeleton, Switch, Table, Tabs, Toggle, ToggleGroup, Tooltip (DesktopShell and Cover are previews only, not components).
- First override batch (the 18 shadcn components the first consumers use): Badge, Button, Card, Chart, Checkbox, Collapsible, DropdownMenu, Input, Label, NavigationMenu, Pagination, Popover, Separator, Sheet, Skeleton, Table, Toggle, ToggleGroup. **All 18 are done**, and so are the other seven (Alert, Article, Kbd, Select, Switch, Tabs, Tooltip): the whole component set above is built. Two of them build on another: `sheet` depends on `@patina/button` and `toggle-group` on `@patina/toggle` (registry dependencies, imported relatively as `./button` and `./toggle`), and `chart` asks for `recharts@^3.8.0` (the release the stock shadcn chart pins is the floor; a newer 3.x already in a project is kept, and 4.x is excluded because the chart styles recharts' own class names; 3.10.1 passes `tests/chart*.test.tsx`). Stock components that depend on one of the finished ones (for example `alert-dialog` needs `button`) will ask before overwriting the Patina file: answer no.
- Chart: `chart-1…5` is a sequential teal ramp, not categorical; a single series uses `chart-3` (`chart-4` on hover). Light and dark have their own values so that every step is at least 3:1 on `background` and `card` (WCAG 1.4.11, enforced in `src/contrast.ts`): lightest to darkest in light, lightest to dimmest in dark. Label series directly rather than by hue alone.
- Icons: Phosphor, regular weight, fill only for selected/active. Web uses `@phosphor-icons/react`, Slint uses SVG via `@image-url`.
- The shadcn docs cover namespaces, `{name}` / `{style}` URL placeholders, `registryDependencies` across namespaces and `shadcn build` to `public/r`. They also document the `registry:base` item itself: `extends: "none"`, `config` (style, iconLibrary, `tailwind.baseColor`, aliases), `dependencies`, `registryDependencies`, `cssVars` (`theme`, `light`, `dark`) and `css`, and that resolved registry files are deduplicated by target path (last one wins). `src/emit/registry.ts` sticks to those fields.
- **Verified with a real install** (2026-10-16, `shadcn` 4.21.5, `r/base.json` served from a local static server, into a scratch Astro 7 + React + Tailwind 4.3 project):
  - `shadcn init <url> --yes` accepts a `registry:base` item. It writes `components.json` from `config` (`style`, `baseColor`, `iconLibrary`), installs `dependencies` (`cn` among them) and writes `cssVars` into the Tailwind CSS file: `@theme inline`, `:root`, `.dark`. The `css` entries land after `@import "tailwindcss"` (`@import` lines, then `@layer base` with `@apply`). It adds `@custom-variant dark (&:is(.dark *))` itself.
  - **`config.style` must be a style that exists at ui.shadcn.com.** Built-in names (every stock component added later, and `utils` for an item that names it) resolve to `https://ui.shadcn.com/r/styles/{style}/{name}.json`. The first attempt with `style: "patina"` failed with a 404 on `utils.json`; `base-luma` works, and is the right lineage.
  - `iconLibrary: "phosphor"` is accepted and used: a stock `dropdown-menu` added afterwards imports `CaretRightIcon` and `CheckIcon` from `@phosphor-icons/react` and `@base-ui/react/menu`. `baseColor: "mist"` is accepted and written to `components.json`.
  - The CLI also copies every non-colour variable into `@theme inline` as `--x: var(--x)` (`--shadow-card`, `--control-md`, `--link` …). This is harmless: those lines sit in `@layer theme` and the unlayered `:root` / `.dark` declarations win. Checked in a browser: dark values apply, and `shadow-card` even becomes a working utility.
  - Compiled output: `text-link`, `bg-primary-hover` (hover only), `rounded-lg` = `var(--radius)` = 8px, `rounded-xl` = 10px, `rounded-2xl` = 12px, `rounded-3xl` = 16px, `font-heading`, `font-serif`, `shadow-(--shadow-menu)` and `h-(--control-md)` all resolve. The Fontsource and Pretendard CSS is bundled with 122 `woff2` files in `dist`, so the fonts are self-hosted.
  - Overriding a built-in: an item named like a built-in with the same target path (`@patina/button` installing `ui/button.tsx`) installs fine. Adding a stock component that depends on the built-in `button` afterwards asks "The file button.tsx already exists. Would you like to overwrite?" (default N; `--yes` does not skip it, and without a TTY the add aborts). So install Patina items first, answer N, and never pass `--overwrite`. Not tested: answering N in a TTY and continuing.
- Still **undocumented and untested**: writing `@font-face` entries in an item's `css` (the base item omits them; D2Coding and MaruBuri `@font-face` rules have to be added by the consumer or shipped as a CSS file).
- Reproducing the check: serve `public/` with any static server, `shadcn init http://127.0.0.1:<port>/r/base.json --yes` in an Astro project that already has Tailwind 4 and an `@/*` alias. Scaffold the project by hand (`package.json`, `astro.config.mjs` with `@astrojs/react` and `@tailwindcss/vite`, `tsconfig.json`, a CSS file with `@import "tailwindcss";`) and add `shadcn` as a dev dependency, which keeps the check independent of template versions. `pnpm smoke` automates exactly this.
- Consumers install with `shadcn add @patina/<name>`. Review the diff before overwriting; never use `--overwrite` blindly.

## Slint library

- Layout: `slint/patina.slint` is the entry file (re-exports the tokens and the components), `slint/components/*.slint` has one file per component, and the build adds the generated `slint/tokens.slint` next to them and an archive of the folder (`src/emit/archive.ts`, no dependencies, deterministic). Consumers unpack the archive into their project, register `patina.slint` as the library `patina` and import from `@patina`, the same shape as `std-widgets.slint` and the Material 3 library. `src/slint-lib.ts` reads the sources; `src/generate.ts` writes them out. The sources import `tokens.slint`, which only the build generates, so `pnpm build` also writes a copy to `slint/tokens.slint` (git-ignored, skipped by the loader) so that slint-lsp and editors resolve the import when you open a file from the repo; without a build the editor reports `Cannot find requested import "tokens.slint"`.
- Done (tier 1, compact density for dense desktop tools, taken from the DesktopShell preview): Button, Input, Badge, Kbd, Tooltip (through a component's `tooltip` property), Separator, TreeRow, ListRow, PaneHeader. Tier 2 (compact too): Checkbox, Switch (the web `sm` size, 28x16), Tabs, Select, Menu (`Menu`, `MenuItem`, `MenuLabel`, `MenuSeparator`) and Table (`Table`, `TableColumn`). Tier 3, only what a desktop tool needs: Alert (`AlertVariant`), Card, Collapsible and Toggle. Left out on purpose: Label (a `Text` with `compact-label` does it), ToggleGroup (Tabs for one choice, several Toggles side by side for independent ones), Popover and Sheet (a `PopupWindow` with a Card or Menu surface), Skeleton, NavigationMenu, Pagination, Article and Chart (web patterns with no desktop counterpart yet). Add one when an app needs it. The list comes from the DesktopShell notes.
- Tier 3 notes: `Card` has no `interactive` hover (the web strengthens the shadow ring, which Slint cannot draw) and uses `radius-xl` and `space-4` padding; `Alert` takes its action as a child at the trailing end; `Collapsible` keeps its children in the tree and hides them while closed; `Toggle` uses `checked` and `toggled(bool)` like Checkbox and Switch, where the web calls the state `pressed`.
- Tier 2 notes: a menu is a surface plus rows that the caller shows in a `PopupWindow` under its trigger (`Select` does this itself); the library has no shadows, so the menu surface has a 1px `border` where the web has a shadow ring. `Select` handles Up/Down (change) and Enter/Space (open) on the trigger only; arrow navigation inside the open list is not built. `Tabs` is the track only, the panels belong to the caller, and Left/Right move the selection. `Table` scrolls its rows through a plain `Flickable` (mouse wheel, no scrollbar) under a fixed header and has no tabular numerals or sorting. The Switch thumb moves with a 100ms animation; nothing else animates.
- Rules: every colour, size, radius and spacing comes from `Theme` and `Typography` (`tests/slint-library.test.ts` rejects colour literals and fixed radii or paddings); sizes that the design fixes without a token (badge 20px, kbd 22px, 1px borders) are the only literals. Components use the compact tokens (`compact-control` 28px, `radius-md`, `compact-label`). No `color-mix`-style tricks: hover and tint colours are tokens.
- How the web behaviour maps: the focus ring is a 2px `ring` rectangle 2px outside the control and appears only for keyboard focus (`FocusReason.tab-navigation`); pressed moves the content 1px down (the whole button cannot move inside a layout); the `link` button has no hover underline; there are no shadows in the library (CSS box-shadow lists have no Slint form); a tooltip opens after 500ms of hover through a `PopupWindow`.
- Things learned: a fixed-height child of a `HorizontalLayout` is placed at the top, not centred, so each control is a transparent slot (at least its height, `vertical-stretch: 0`) with the visible `body` centred in it; `parent` cannot be used on a component's root element, so a helper such as `FocusRing` takes `host-width` and `host-height`; `text` as an `accessible-role` value clashes with a `text` property, write `AccessibleRole.text`; `TextInput` has no `mouse-cursor`; `PopupWindow` `x` and `y` are relative to its parent element and headless screenshots ignore them, so the tooltip position is not verified by a render; `--load-data` reaches a global only if the main file exports it (`export { Theme }` in the gallery); in a layout, `preferred-width` of a component must not count padding twice when the inner layout already has it.
- Verification: `pnpm slint:shot` builds, then renders `scripts/slint/gallery.slint` (`Shell` is the DesktopShell preview built from the library, `Board` has every tier 1 variant, `Controls` every tier 2 state, `Panels` every tier 3 state) in light and dark into `slint-shots/` (git-ignored) with `slint-viewer`, which comes from the Slint releases (`slint-viewer` and `slint-lsp`, version 1.18 or newer, on `PATH`). ## Conventions

- Tooling: pnpm 11 (`packageManager` pinned), Node `^22.12.0 || ^24.11.0`, TypeScript, ESLint + Prettier, Vitest, lefthook (pre-commit: tsc/eslint/prettier; pre-push: tests), `wrangler.jsonc`.
- Commands that exist: `pnpm check` (tsc + eslint + prettier check + vitest run), `pnpm typecheck`, `pnpm lint`, `pnpm format`, `pnpm test` (vitest watch). Tests cover the snapshot (`tests/snapshot.test.ts`), the token parser (`tests/tokens.test.ts`), the colour math (`tests/color.test.ts`) and the Material 3 mapping (`tests/m3.test.ts`), the derived tokens (`tests/derived.test.ts`), the contrast baselines (`tests/contrast.test.ts`), the generated files (`tests/emit.test.ts`, `tests/android.test.ts`, `tests/slint.test.ts`, `tests/fonts.test.ts`), the component items (`tests/registry-items.test.ts`) and the components themselves, rendered on the server (`tests/components.test.tsx`).
- `pnpm build` verifies the snapshot (`src/verify.ts`), then writes `public/` (`scripts/build.ts` calls the pure `generate()` in `src/generate.ts`); it exits 1 and prints every failed check if the tokens are inconsistent. `pnpm deploy` is `pnpm build && wrangler deploy`; `wrangler.jsonc` serves `./public` as static assets on `patina.ptcookie.net`. `public/` is generated and git-ignored.
- `pnpm smoke` (`scripts/smoke.ts`) installs the generated base item with the real shadcn CLI and checks the result; it needs the network (npm registry, ui.shadcn.com), takes about 20 seconds with a warm package cache, and is deliberately not part of `pnpm check`. It builds the files in memory, serves them from a local HTTP server, creates a scratch Astro + React + Tailwind 4 project in a temp directory, runs `shadcn init <url> --yes` and `shadcn add accordion --yes`, then `astro build`, and makes about 235 checks (the project's own `src/lib/utils.ts`, written before `init` and without `cn`, must be byte-identical after `init` and every add; the base item has no registry dependencies for this reason): `components.json` (`base-luma`, `mist`, `phosphor`), every base dependency installed, the font `@import` lines, every `cssVars` entry present in `@theme inline` / `:root` / `.dark`; then `shadcn add @patina/*` for every component through the `@patina` namespace, leaving `button` and `toggle` off the command line so they must arrive as registry dependencies (each file equals its source, no `color-mix`, `sheet.tsx` imports `./button`, `recharts` is installed); the stock component rewritten to Phosphor and Base UI; the compiled utilities (theme utilities such as `text-link` and `rounded-xl`, and the ones the components need such as `h-(--control-md)`, `bg-outline-fill`, `shadow-(--shadow-card)`); the server-rendered classes of a page that uses the components (variants replace defaults, the pill drops `rounded-lg`, the interactive card gets its hover shadow). The chart bars are not asserted: `ResponsiveContainer` has no size on the server, so they render on the client only; `tsc --noEmit` on the installed components; and bundled `woff2` files. It exits 1 with the failed checks and removes the temp directory afterwards (`PATINA_SMOKE_KEEP=1` keeps it and prints the path). The dependencies are installed at their latest versions on purpose, so a run also shows when a new shadcn, Astro or Tailwind release breaks the item. The CLI requests `/r/base.json?base=base`: a test server has to ignore the query string, as static hosts do.

## Gotchas

- The build runs as `node --import tsx scripts/build.ts`: `tsx` is loaded as an in-process loader, so no separate `tsx` child process is started.
- Spacing tokens (`space-N` = N * 4px) equal the Tailwind default scale, so the registry item omits them (`spacingMatchesTailwind` asserts this in tests). Slint gets them as `space-1-5` for `space-1.5`; dots are not valid in Slint identifiers or CSS variable keys.
- Shadow tokens are CSS box-shadow lists: they are root variables on the web (`shadow-(--shadow-card)`) and are not emitted for Slint or Android.
- `src/color.ts` (port of `tools/cc.py`), `src/tokens.ts` (parser, `{ref}` resolution) and `src/m3.ts` (port of `tools/m3.py`) must keep producing the Python numbers. `tests/fixtures/m3.json` holds the reference contrast and hex values; regenerate it with `python3 tools/m3_fixture.py` only when tokens or the mapping change on purpose, and review the diff. `tests/m3.test.ts` also checks that the Kotlin blocks in `design-system/Android.md` equal the computed hex values.
- `src/derived.ts` holds one recipe per row of the "Derived tokens" table and `checkDerived(set)` returns every token that disagrees with its recipe (the build must fail on a non-empty result). When you add or change a derived token, update the table in this file and `DERIVED` together: `tests/derived.test.ts` compares the two. `tokens.json` prints L, C and H with 3 decimals, so values are compared with a ±0.0005 tolerance; alpha is compared exactly.
- `src/contrast.ts` turns the accessibility prose (token `usage` notes, `design-system/README.md` § Accessibility) into requirements and measures them on the real colours; translucent tints are composited over the surface they sit on. `checkContrast(set)` returns every failing requirement (the build must fail on a non-empty result). `min` is the number the prose promises. The notes were corrected after the first measurement (dark `foreground` on `muted`/`accent` is 14.25:1, dark `link` on `muted` is 5.9989:1), so they say 14 and 5.9, not 15 and 6. When you change a ratio in a usage note, update the matching requirement; `tests/contrast.test.ts` fails if a note states a ratio no requirement knows.
- Fractional alpha exists in the tokens (`4.5%`, `7.5%`, `13.5%`). `tools/cc.py` cannot parse it (its regex takes integer percentages); the TypeScript parser does. Those tokens are not in any M3 pair, so the fixtures are unaffected.
- Keep `typescript` on 6.x: `typescript-eslint` 8.71 rejects TypeScript 7 (peer range `<6.1.0`). Revisit when typescript-eslint supports 7.
- The git hooks (`lefthook.yml`) are installed by `pnpm install` through the `prepare` script in a git checkout; run `pnpm exec lefthook install` to reinstall them. Pre-commit type-checks, lints and formats staged `.js`/`.ts`/`.tsx` files; pre-push runs the tests.
- Astro: a React component nested inside another component in a `.astro` file is a separate island and loses React context (the chart tooltip throws "useChart must be used within ChartContainer"). Compose context-based components inside one `.tsx` file, as the smoke test does with `src/components/demo.tsx`.
- Class variants only work if Base UI really emits the attribute: the Separator uses `data-orientation`, `NavigationMenu.Link` has no `data-highlighted` (only `data-active`), and Recharts' class names change between releases. `tests/chart-markup.test.tsx` draws a real chart and checks every selector in `ChartContainer` still matches; `tests/components-static.test.tsx` checks the separator attribute. When you add a `data-*` variant, confirm the attribute in `@base-ui/react/<part>/*DataAttributes.js`.
- Base UI's Checkbox puts the `id` on its hidden input, not on the root; select it by `data-slot="checkbox"` in tests.
- Tailwind merges identical rules into one selector list (`.shadow-\(--shadow-card\),.shadow-card{…}`), and server markup HTML-escapes class names (`&amp;`, `&gt;`, `&#x27;`): decode before comparing, and match CSS needles on the selector, not on the whole rule.
- Pill-shape rules must come last in `bundle.css` (source order beat specificity once).
- Repeating the parity check needs a scratch project like the smoke test's (`PATINA_SMOKE_KEEP=1 pnpm smoke` keeps one): one page that renders the preview bodies with `bundle.css` and `bundle.js`, one that renders the Patina components, both with the same token variables (`:root`, `.dark`, the `--radius-*` and `--font-*` variables from `@theme inline`, and `--space-N`; put the font `@import` lines first in the CSS or the spec page silently falls back to system fonts), loaded in two same-origin iframes and compared pair by pair with `getComputedStyle`. Preview-only artefacts to filter: the previews have no `box-sizing` reset (widths differ by borders), Tailwind's preflight resets buttons and borders, a bundler may drop `backdrop-filter` from the spec CSS, and a static server must not serve from a directory that a rebuild deletes. The browser pane's pointer coordinates are scaled (800x600 for a 1280x900 viewport), so scale hover coordinates per axis.
- Visual regression used during design (not carried over): render every preview in light and dark with Playwright, pixel-diff before/after, plus computed-style comparison at rest and hover, plus interaction tests. Reproduce it if the previews or `bundle.css` change.
